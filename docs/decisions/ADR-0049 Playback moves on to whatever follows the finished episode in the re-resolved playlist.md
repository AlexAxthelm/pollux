# Playback moves on to whatever follows the finished episode in the re-resolved playlist

## Context

A playlist is a query, so its list changes while the user listens. A playback-status filter such as "not played" removes the current episode as soon as it is played. Episodes can arrive, and the user can edit the playlist while it plays. "Next" has to mean something in each of these cases. [[ADR-0006 No auto-advance until playlists exist]] was written as a temporary rule until playlists could define a next episode.

## Decision

Each time playback moves on automatically, the playlist is **resolved again** and the next episode is the one that comes **after the episode that just finished, in the active playlist's order**. The list is resolved at **the last moment the finished episode was still active**: just before it is marked played, and with every edit made while it played already in effect. "Next" is read from that list, so edits and new episodes made while the episode played are in it. It is not read from the moment the episode was loaded. At a normal advance nothing else is needed to keep the finished episode in its place: the list is resolved just before the episode is marked played, so its status has not changed. The **anchor** (below) is for the few cases where something has changed since.

**Worked examples.** The playlist has a "not played" filter, so each episode drops out of the list once it is played.

- The list is `[A, B, C, D, E]` and C is playing. When C finishes, D plays next. If, while C played, the user rearranged it to `[A, C, E, D, B]`, then E plays next: C is still in the list at that moment, and E is what follows it.
- With Deduplicate off an episode can appear twice, and the playing copy is the one with the same route. The list is `[A, B, C1, D, E, C2, F, G]` and C1 is playing: D plays next. If it is rearranged to `[C2, A, B, D, E, F, C1, G]`, then G plays next, because C1 is the copy that is playing and G follows it. C2 is not.

- Starting an episode from the middle of a playlist makes that playlist active and plays from that episode's position ([[ADR-0029 The active playlist is set by where playback started]]).
- Episodes added right after the current one play next. If the current episode is moved to the top, whatever follows it in the new order plays next.
- Queued episodes play before this, as in [[ADR-0046 Queued episodes play before the active playlist resumes]].
- The playlist becomes inactive when nothing follows the finished episode.
- **Status changes are held in place; list changes are not.** The playing episode can be missing from the rebuilt list for two different reasons.
  - **Its status changed:** it was marked played when it finished, or the listener marked it played by hand while it played, or its position was reset to zero (which drops it from an "in progress" filter). The anchor holds it in place against **playback-status filters**, so the playlist carries on with what follows it. A manual mark on the playing episode therefore does not stop the playlist.
  - **The list itself changed:** an edit removed its source, a feed refresh or new episodes pushed it past First N episodes, or an included playlist stopped providing it. Nothing holds it in place. It keeps playing with its current settings, and when it finishes the list is resolved at that moment and, if the episode is not in it, playback ends. If it left and came back before it finished, it is in the list and playback continues after it. A "newest first, then First 3" playlist can therefore stop after a long episode, because new episodes pushed it out; that is accepted.
  The playlist is not a context for anything after a stop.
- **The anchor.** The resolver takes an optional **anchor**, the playing occurrence, which the playback-status filters treat as passing (as it was at its last moment, not played and in progress), so that it is still in its place; every other rule treats it like any other episode. **It is unused at a normal advance.** It is used only (1) when the episode's status was changed while it played, by marking it played by hand; (2) when a status filter was edited while it played (the next bullet); and (3) when a queue empties, where the finished episode was marked played long before ([[ADR-0046 Queued episodes play before the active playlist resumes]]). For a queue drain the anchor is stored with the play context, so it survives a restart. Nothing about the episode's position needs to be stored, because the anchor bypasses the status filters rather than reconstructing the status.
- **Editing a status filter while an episode plays does not remove it.** The anchor holds the playing episode against every playback-status filter, edited or not, so the edit applies from the next episode. Example: E is playing from P with "include Not played", and P is changed to "include Played". Playback carries on after E. That is where a fresh look would put E anyway, because once E finishes it is marked played and belongs in the new list. The other edits that take an episode out (removing its source, adding a title filter, a First N cut) are not status filters, so the anchor does not hold against them and playback stops after E. The removal warning ([[US-0250 Be warned before removing the playing episode from its playlist]]) is about those.
- **The next episode must be in the resolved list.** The resolver runs at that moment, so an episode that no longer qualifies is never chosen, and the chosen episode is not checked again afterwards. If the second copy of the same episode is what follows the finished one in the list, it plays, even though that episode has now been marked played. The finished copy is the one identified by its route, as in the example above.
- **If the active playlist is deleted**, it is the same case as an edit that removes the playing episode: the playing episode finishes with the context it started with, and playback then ends. The queue keeps playing, because it is not part of the playlist ([[ADR-0046 Queued episodes play before the active playlist resumes]]), and playback ends when it empties, since there is no playlist to resume. Other playlists that include the deleted one drop it as a source. The delete confirmation says when the playlist is playing ("It is playing now; it will finish this episode and stop"). The player's "From:" row then keeps the playlist's name as it was when the episode started, and is not tappable ([[player]]).
- **If the app closes and restarts before the playing episode has finished**, the episode is reopened with its stored context (the route and resolved settings), also when its playlist has since been deleted or changed. Restoring an active context restores that context. Once the episode finishes, playback ends as above. An episode that was marked played by hand is not restored, as [[ADR-0012 The play context is restored on launch with capped save retries]] says.
- Pausing near the end of an episode does not finish it; see [[ADR-0052 Pausing near the end does not mark an episode played]].
- **A failed resolution** (the work bound is passed, [[ADR-0053 Resolution is bounded by the work it does, and playlists have no episode limit]], or a storage read fails) is different from an empty playlist, which is valid, and from reaching the end.
  - **Activating a playlist** resolves it first. If it fails, the current playlist keeps playing, the new one shows "This playlist could not be loaded", and nothing is evicted. An empty playlist is valid to have and to view, but it is not activated: pressing play on it leaves the current playback alone and shows "This playlist is empty".
  - **At an advance,** the finished episode is completed as usual (marked played, position reset, saved context cleared, [[ADR-0002 Played is decided when the listener leaves an episode]]). In the running session the player stays on the playlist with the anchor kept in memory, shows "Couldn't load the playlist", and Play retries the resolution, not the episode that finished. This waiting state is **not saved**: if the app restarts first, the player is inactive and nothing is restored. A failure can happen if the library or the rules changed so that the resolution now costs more than the bound, or on a transient read error.
  - **A restore still resumes the stored episode** with its stored context, as it does when its playlist has been deleted. The rule above applies when that episode finishes.
  - **The library's compact rows** show their counts as each resolution completes, without a loading screen ([[US-0238 The app opens straight into the library without a loading screen]]), and a playlist that fails shows a small error state on its row.
- **Edits take effect on Save.** A change to sources or rules first changes playback at the next automatic advance. A change to settings shows in the editor straight away; it reaches the playing episode at once only if it is at a level on that episode's route and every step of that route still exists, and otherwise from the next episode ([[ADR-0044 An episode's settings come from the context it is played from]]).
- **Which copy of the finished episode counts.** With Deduplicate off an episode can appear twice. "After the finished episode" means after the occurrence with the same episode and route, or after the first occurrence if that route is gone.
- The alternate setting "From the top" plays the first episode that is **not played** ( [[playlists-rules]]) in the list resolved at that moment, counting the episode that just finished as played so it is not picked again, instead of the one after the finished episode, and playback ends if every episode is played. It changes only how the successor is chosen: if the current episode has left the list for a list change (an edit, a refresh, a First N cut), playback still ends after it, as above. Skipping played episodes is what stops it replaying the first episode forever ([[playlists-playback]], [[US-0254 Be warned about settings that make a playlist replay]]).

## Consequences

- Resolution runs on each advance, so it has to be fast, and it is bounded by the work bound ([[ADR-0053 Resolution is bounded by the work it does, and playlists have no episode limit]]).
- The auto-advance in [[ADR-0006 No auto-advance until playlists exist]] is replaced by this rule once playlist playback is built. That ADR is left as it stands until then.
- The playing episode's context route is fixed when it starts and stays fixed until it ends ([[ADR-0044 An episode's settings come from the context it is played from]]), so an edit that changes the route cannot change its settings mid-episode. A settings edit at a level on the route does reach it at once, which re-resolves along the same route, while every step of the route still exists ([[ADR-0044 An episode's settings come from the context it is played from]]).
